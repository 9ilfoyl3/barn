# Agent Note: Barn Desktop targets macOS and Windows from the same codebase

Status: proposed

## Problem

Barn Desktop must be installable and usable on macOS and Windows. Platform-specific paths, key shortcuts, window chrome, process sandboxing, and packaging cannot leak into Agent or UI contracts as macOS assumptions.

## Proposal

Desktop code uses Electron `app.getPath()` for user data and documents, `process.platform` only through typed environment capabilities, and platform-neutral Session, output, model, and IPC contracts.

Renderer labels shortcuts as Command on macOS and Ctrl on Windows. BrowserWindow chrome selects the native macOS title-bar style only on macOS. Packaging uses electron-builder targets for DMG/ZIP and NSIS.

Shell execution uses a platform backend registry. A platform without a sandbox backend that enforces the requested policy fails closed rather than running unconfined.

## Alternatives considered

**Maintain separate macOS and Windows applications.** Rejected because it duplicates the Agent, model configuration, Session format, and most UI behavior.

**Assume POSIX paths and shortcuts.** Rejected because it breaks Windows installs and makes tests misleading.

**Fall back to unrestricted shell on Windows.** Rejected because model-driven command execution without an enforced sandbox violates the security boundary.

## Acceptance criteria

- the Desktop builds on macOS and Windows CI runners;
- user data and output paths use Electron platform APIs;
- command shortcuts render per platform;
- Session and model contracts contain no POSIX-only paths;
- Windows shell is unavailable until an enforcing backend exists;
- macOS and Windows installers are generated by electron-builder.

## Risks

- Windows sandbox backend delivery may lag the application shell.
- Native packaging and signing require platform-specific credentials.
- Platform-specific path casing and filesystem permissions need explicit tests.
